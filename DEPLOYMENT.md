# Deploying Faith Hill to Render + Supabase

This guide takes the repository from "works on my laptop" to a live site with
three moving parts:

| Piece | Host | What it does |
|---|---|---|
| **API** (Django) | Render web service | Serves content, accepts form submissions, runs the staff CRUD API |
| **Postgres** | Supabase | Stores all content, submissions and staff accounts |
| **Image storage** | Supabase Storage | Holds uploaded photos (Render's disk is wiped on every deploy) |
| **Public website** | Render static site | The church site visitors see |
| **Staff console** | Render static site | Content management, on an unguessable path |
| **Videos** | YouTube | Sermons stay on your channel; the site embeds the player |

Total cost on Render's free tier: **$0**. Supabase free tier: **$0**.

---

## 0. Before you start

You need:

- A [Render](https://render.com) account connected to the GitHub repo
- A [Supabase](https://supabase.com) account
- A YouTube channel (videos uploaded there — the site only needs the watch URLs)
- This repository pushed to GitHub (already done)

---

## 1. Supabase — database

1. Create a project at [database.new](https://database.new).
   - **Region:** choose the closest to your congregation — `Europe (Frankfurt)`
     pairs well with Render's Frankfurt region.
   - **Save the database password** somewhere safe. It appears once.
2. Wait for provisioning (~2 minutes), then click **Connect** (top of the page).
3. Choose the **Connection pooling** tab → **Session mode** → copy the URI.
   It looks like:

   ```
   postgresql://postgres.abcdefghijklmnop:[YOUR-PASSWORD]@aws-0-eu-central-1.pooler.supabase.com:5432/postgres
   ```

4. Replace `[YOUR-PASSWORD]` with the real password. This whole string is your
   `DATABASE_URL`.

> **Why session mode?** Django keeps long-lived connections. Supabase's
> *transaction* mode (port 6543) is meant for serverless functions and will
> break Django's prepared statements. Session mode (port 5432) is correct here.

> **SSL** is required and is on by default. If you ever need to bypass it, set
> `DATABASE_SSL_DISABLE=True` — not recommended.

---

## 2. Supabase — image storage

Render containers are ephemeral: a photo uploaded today is gone after the next
deploy. Uploads therefore go to Supabase Storage.

1. In Supabase, go to **Storage** → **New bucket**.
2. Name it exactly **`faithhill-media`**.
3. Toggle **Public bucket** ON. (Public = anyone can *read* an image by URL;
   writes still require the service key, which only the API holds.)
4. Go to **Project Settings** → **API** and copy:
   - **Project URL** → the subdomain is your project ref
     (`https://abcdefghijklmnop.supabase.co` → `abcdefghijklmnop`)
   - **service_role** secret key (under "Project API keys")

> ⚠️ **The `service_role` key bypasses all row-level security.** It is only ever
> used server-side, as a Render environment variable. Never put it in a frontend,
> never commit it, never paste it into a chat window.

Optional hardening: Supabase can generate dedicated S3 credentials
(**Storage → S3 access keys**). If you make them, set them as
`SUPABASE_ACCESS_KEY` and keep the service key for `SUPABASE_SERVICE_KEY`.

---

## 3. Render — deploy the blueprint

The repo contains `render.yaml`, which defines all three services.

1. Render dashboard → **New +** → **Blueprint**.
2. Select this repository. Render reads `render.yaml` and shows three services:
   `faith-hill-api`, `faith-hill-website`, `fh-staff-console`.
3. It will prompt for the values marked `sync: false`. Fill them in:

   | Variable | Value |
   |---|---|
   | `DATABASE_URL` | the Supabase session-pooler URI from step 1 |
   | `SUPABASE_PROJECT_REF` | your 20-character project ref |
   | `SUPABASE_SERVICE_KEY` | the `service_role` key |
   | `ALLOWED_HOSTS` | `faith-hill-api.onrender.com,faithhill.org,www.faithhill.org` |
   | `CORS_ALLOWED_ORIGINS` | `https://faith-hill-website.onrender.com,https://your-staff-console.onrender.com` |
   | `CSRF_TRUSTED_ORIGINS` | same two origins |
   | `VITE_API_URL` (both frontends) | `https://faith-hill-api.onrender.com` |
   | `VITE_BASE_PATH` (staff only) | your secret path, e.g. `/fh-console-7x2k9/` |

   You can leave `ALLOWED_HOSTS` / `CORS_*` minimal at first and fill in real
   domains after you see the generated URLs.
4. Click **Apply**. First deploy takes ~5 minutes (installs packages, migrates
   the database, collects static files).

`SECRET_KEY` is generated by Render automatically — you never see or set it.

## 4. Create your staff account

The database starts empty, so there is no login yet. Locally, with your
`DATABASE_URL` pointing at Supabase:

```bash
cd backend
python3 -m venv faithhill/.venv
faithhill/.venv/bin/pip install -r requirements.txt

cd faithhill
export DATABASE_URL='postgresql://postgres.xxxx:PASSWORD@aws-0-eu-central-1.pooler.supabase.com:5432/postgres'
export SUPABASE_PROJECT_REF='xxxx'
export SUPABASE_SERVICE_KEY='service-role-key'

.venv/bin/python manage.py migrate
.venv/bin/python manage.py createsuperuser   # choose a strong password
```

Prefer not to export secrets in your shell? Create `backend/faithhill/.env` and
load it with `set -a; source .env; set +a` (the file is gitignored).

To load the demo content instead (services, sample sermons/events):

```bash
.venv/bin/python manage.py seed_demo
```

A superuser can log into both Django admin (`/admin/`) and the staff console.

## 5. Publish your first sermon (YouTube)

1. Upload the video to YouTube as usual.
2. Copy the link — **any** of these shapes works:
   - `https://youtu.be/VIDEO_ID`
   - `https://www.youtube.com/watch?v=VIDEO_ID`
   - `https://www.youtube.com/live/VIDEO_ID` (from a livestream)
   - the whole `<iframe …>` embed snippet
   - just the bare `VIDEO_ID`
3. In the staff console → **Sermons** → **New sermon**, paste it into
   **Video URL**.
4. The API rewrites it to a canonical watch link, derives the video id, and
   falls back to the YouTube poster frame for the thumbnail if you don't upload
   one.

The site plays videos through `youtube-nocookie.com`, so no tracking cookies are
set until a visitor actually hits play. If a video is private or unlisted,
unlisted works fine; private will not play for visitors.

## 6. The staff console's secret path

Set `VITE_BASE_PATH` on the `fh-staff-console` service to something long and
random, for example:

```
/fh-console-7x2k9/
```

Then staff bookmark `https://<staff-site>.onrender.com/fh-console-7x2k9/`.
Any other path on that host shows the login screen too — but **the path is not
the security boundary.** What actually protects the data:

| Layer | Where |
|---|---|
| Every API call requires a valid JWT | `DEFAULT_PERMISSION_CLASSES: IsAdminUser` |
| The account must have `is_staff` | `MeView`, all `/api/manage/` viewsets |
| Login is rate-limited (10/min) | `ThrottledTokenObtainPairView` |
| Search engines are told to stay out | `X-Robots-Tag: noindex` header |
| HTTPS only, HSTS preload | production hardening block |

Treat the long path as a curtain, not a vault. A strong password is the lock.

## 7. Custom domain

1. Render → your public website service → **Settings** → **Custom Domains** →
   add `faithhill.org` and `www.faithhill.org`.
2. At your DNS provider, add the CNAME records Render shows you.
3. Then update on the **API** service:
   - `ALLOWED_HOSTS` → add `faithhill.org,www.faithhill.org`
   - `CORS_ALLOWED_ORIGINS` → add `https://faithhill.org,https://www.faithhill.org`
   - `CSRF_TRUSTED_ORIGINS` → same
4. Redeploy the API. Then rebuild both frontends if you move them to custom
   domains too (`VITE_API_URL` stays pointed at the API).

## 8. Free tier realities

| Behaviour | Effect | Mitigation |
|---|---|---|
| API sleeps after 15 min idle | First visitor waits ~30-50 s for a cold start | None on free tier. Upgrade to Starter ($7/mo) if this matters for Sunday mornings. |
| Static sites never sleep | Website loads instantly; API calls may be slow on first hit | The public site shows its loading state |
| 750 instance hours/month | One always-on service fits; two do not | Keep a single API service |
| Ephemeral disk | Uploaded files vanish on redeploy | Already solved: Supabase Storage |
| No cron jobs | Can't schedule tasks | Not needed — YouTube sync is manual by design |

> **Sunday morning tip:** the API cold start is the one free-tier annoyance
> visitors will notice. If the church has budget, move only `faith-hill-api` to
> Starter and leave the frontends free.

## 9. Environment variable reference

### API service

| Variable | Required | Purpose |
|---|---|---|
| `SECRET_KEY` | ✅ (auto) | Django signing key; Render generates it |
| `DEBUG` | ✅ | Must be `False` in production |
| `DATABASE_URL` | ✅ | Supabase Postgres connection string |
| `SUPABASE_PROJECT_REF` | ✅ | Storage endpoint + public URL base |
| `SUPABASE_SERVICE_KEY` | ✅ | Storage write access |
| `SUPABASE_BUCKET` | — | Defaults to `faithhill-media` |
| `ALLOWED_HOSTS` | ✅ | Comma-separated hostnames |
| `CORS_ALLOWED_ORIGINS` | ✅ | Origins allowed to call the API |
| `CSRF_TRUSTED_ORIGINS` | ✅ | Origins trusted for admin/CSRF |
| `THROTTLE_LOGIN` | — | Default `10/min` |
| `THROTTLE_SUBMIT` | — | Default `30/hour` |
| `LOG_LEVEL` | — | Default `INFO` |
| `ALLOW_SQLITE_IN_PRODUCTION` | — | Escape hatch; leave unset |

### Both frontend services

| Variable | Purpose |
|---|---|
| `VITE_API_URL` | API origin, e.g. `https://faith-hill-api.onrender.com` |
| `VITE_BASE_PATH` | Staff console only: secret path prefix |

> Frontend variables are compiled in at **build** time. Changing one requires a
> redeploy of that static site, not just a restart.

## 10. Smoke test after deploying

```bash
API=https://faith-hill-api.onrender.com

curl $API/api/health/                 # {"status":"ok","database":"ok"}
curl $API/api/sermons/                # your sermons
curl $API/api/service-times/          # service times
curl -X POST $API/api/submit/prayer-request/ \
  -H 'Content-Type: application/json' \
  -d '{"name":"Test","request":"Checking the form works."}'
```

Then in the browser:

1. Public site loads with real content (not empty placeholders).
2. Open a sermon → video plays.
3. Submit the prayer form → appears in the staff console inbox.
4. Log into the staff console → create a sermon → refresh the public site.
5. Upload an image in the console → confirm the URL starts with
   `https://<ref>.supabase.co/storage/v1/object/public/faithhill-media/`.

If images 404, the bucket is not public or the key lacks write permission.

## 11. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Deploy fails: `DATABASE_URL is not set` | Missing env var (this guard is intentional) | Add it in Render → Environment |
| `DisallowedHost` | Domain not in `ALLOWED_HOSTS` | Add it, redeploy |
| CORS error in the browser console | Missing origin in `CORS_ALLOWED_ORIGINS` | Add it, redeploy |
| Login returns 429 | Throttled (10/min) | Wait a minute |
| Images disappear after redeploy | Storage fell back to local disk | Check the two Supabase storage vars are set |
| `SSL connection is required` | SSL disabled | Unset `DATABASE_SSL_DISABLE` |
| Admin CSS missing | `collectstatic` didn't run | Confirm the build command is `./build.sh` |
| Sermon video blank | Private video, or a URL the parser doesn't recognise | Use Share → Copy link; check Django admin shows a canonical `watch?v=` URL |
